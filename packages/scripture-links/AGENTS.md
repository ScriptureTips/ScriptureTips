# @scripturetips/scripture-links

The shared core of the website plugin and (later) the browser extension (vision §3.6): it finds the scripture references inside part of a page, makes them links, and shows the passage in a tooltip when a reader hovers or taps. Browser code (it needs a DOM), but no framework and no globals, so the extension can build on it and several instances can run on one page.

```ts
import { createScriptureLinks } from "@scripturetips/scripture-links";

const links = createScriptureLinks({ api: "https://scripturetips.org/api" });
links.run("#content"); // and what appears in #content later
links.setPreferences({ translation: "bsb" });
links.on("tooltip-open", (e) => console.log(e.reference));
links.destroy(); // every link is replaced by its words again
```

- **Finding** (`find.ts`): `@scripturetips/reference/light`, the reader every plugin shares, in the KJV's numbering by default (domain-model §2.2), without the versification tables so the script stays small. A page's reference is sent to the server as OSIS with its `scheme`; the server converts.
- **Scanning** (`scan.ts`): a TreeWalker over the text nodes under each matched element. Never scanned, with everything inside them: links (so none is nested), `code`, `pre`, `kbd`, `samp`, scripts, styles, form fields, anything `contenteditable`, `.st-ignore` and `[data-st-ignore]`, the tooltip itself, and anything the `ignore` option names. **A reference split across elements** ("John <b>3</b>:16") **isn't found** (text nodes are read one at a time).
- **Links** (`class="st-ref"`, `data-st-ref` the OSIS, `data-st-text` the words as written): `href` is the destination (`destination.ts`): `scripturetips` (default: the site's `/read?t=&ref=`, which reads the reference in the translation's numbering and redirects to its address) or a URL template with `ST_REFERENCE`, `ST_TRANSLATION`, `ST_BOOKNAME`, `ST_CHAPTER`, `ST_VERSE`. They open in a new tab.
- **Content added later** (`instance.ts`): one MutationObserver on the body, batched (100 ms); added nodes under a scanned area are scanned. The plugin's own changes are dropped from the observer's queue (`takeRecords`), so linking can't loop. `rescan(element?)` looks again by hand.
- **Tooltip** (`tooltip.ts`): in a shadow root (the page's styles don't reach in, its own don't leak out; theme it with `--st-accent`, `--st-ink`, `--st-muted`, `--st-rule`, `--st-paper`, `--st-radius`, `--st-font` on the page), text set only as text, never markup, whatever the API says. A mouse opens it when the pointer rests on a link (`hoverDelayMs`, 300), a keyboard when the link takes focus; it stays while the pointer is over it **or a control in it has the focus** (the translation select's choices open outside the tooltip, so the pointer is off it while the reader chooses; if it's rebuilt as the passage arrives, the select keeps the focus), and goes with Escape, a press elsewhere, the focus moving on, or the pointer leaving when nothing in it has the focus. **After a choice by the pointer the focus is let go** (a choice by the keyboard keeps it), so the tooltip stays visible but isn't held: the pointer going into it and out puts it away, and hovering another link opens that link's. **The link being looked at is outlined** (`a.st-ref[aria-expanded="true"]`, a small style the plugin adds to the page and removes on `destroy`; the page can restyle it), so it's clear which copy of a passage is being edited, and **the tooltip is placed under or above its link, whichever fits and covers fewer of the page's other passage links**, so two copies near each other can each be reached. **A touch screen's first tap opens it instead of following the link**; *Read more* is the way on. It carries the translation switcher, the passage (at most 12 verses, then "…"), the credit statement the license asks for (with its links), and *Read more* (the passage as the translation numbers it, on the site's reader). The layout is minimal: the owner designs the interface later. Keyboard users get the passage on focus; moving into the tooltip with Tab isn't built.
- **Client** (`client.ts`): `GET /api/widget/translations` and `/passage`, with `credentials: "omit"` and no custom headers (no cookie, no preflight), answers kept for the page's life, a failure not kept. `fetch` is an option, since the extension reaches the API through its background script.
- **Which translation a passage opens in** (`translation.ts`, `chooseTranslation`), most explicit first: (1) **what the reader chose for that link** (the translation select in its tooltip: each link is its own, so two copies of one passage on a page can differ), (2) the translation the link's own address names (`t=`), for a link the page wrote; one the plugin made names a translation only because it must, so its `t=` isn't read back (`data-st-auto`), (3) an **abbreviation written right after the passage** in the same text node, in brackets ("John 3:16 (NLT)": `findInText`'s `written`, kept as `data-st-written`, matched to a listed translation's abbreviation without minding case), (4) **the visitor's preference** (`setPreferences`; on our own pages the account's first favorite), (5) **the configured default** (`translation` option), (6) the KJV, or the first listed. A step that names a translation the plugin can't show (the NLT isn't here) is skipped, not the passage.
- **No cookies; the reader's own choices are kept in their browser** (`choices.ts`): a map of link → translation in the page's `localStorage` (`scripturetips:translations`), a link being named by **its own identity** if the page gives one (`data-st-key`, `KEY_ATTRIBUTE`: the study tooltip gives each link's ID, so a choice follows that link whatever else is on the page: `key|<id>`), else by the page's path, the passage (OSIS) and which copy of that passage it is among those on the page (`/blog/post|John.3.16|1` is the second): so a link the plugin scanned is kept per page, and if content is added before a copy the copies may need choosing again. A page that draws its own links and shows only some at a time must give the identity: the count of copies is only right while all are there, written only when the reader chooses, never sent anywhere, with no expiry (it lasts until they clear their browser's storage), the most recent 500 kept. Blocked or full storage means the choices last for the page. The `storage` option replaces it (`null` for the page only; the extension will bring its own). Choosing for one link changes no other, even of the same passage, and a link's address names its own choice. (A passage no link of which has been chosen for is not remembered across pages.)
- **Links drawn by someone else work too.** The tooltip listens for any `a.st-ref` on the page (with `data-st-ref` the OSIS and `data-st-text` the words), whoever made it, so a page that draws its own links (React, say) needn't be scanned: it creates an instance and never calls `run`. The web app does this for the study tooltip's list of links (`apps/web/src/study/StudyPassagePopups.tsx`, canonical numbering, its own `/api/widget`).
- **Events** (`on`): `tooltip-open` (`{ reference, translation }`), `translation-change` (`{ reference, translation }`), `scan`.
- **Strings** are NZ English (`strings.ts`), replaceable through the options.
- **Not built yet:** lite mode, moving and resizing the tooltip, expanding to the paragraph, stepping to the next and previous passage, search in the tooltip, serving publications (public translations only for now), the user's own compilation and a local cache of passages (the extension; vision §3.6, sources.md §8 item 29). The client's `fetch` option is where it plugs in.

Run the tests: `./toolbox pnpm --filter @scripturetips/scripture-links test` (the pure parts: finding, destinations, the client). The DOM behavior is tested end to end in `apps/web/e2e/widget.spec.ts`.
